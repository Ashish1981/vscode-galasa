# Galasa for Visual Studio Code

_This extension is directly linked to the [Java Extension Pack](https://code.visualstudio.com/docs/languages/java) to be able to compile your Java-workspace and to build Galasa-tests using Maven for Java. This is installed simultaneously with the Galasa extension._

## Prerequisites

-   A JDK between version **8 and 26** (inclusive). Any modern OpenJDK distribution will work (Temurin, Zulu, Corretto, Microsoft Build, Liberica, Oracle, etc.). The extension automatically detects the active Java in this order:
    1. The `galasa.javaHome` setting
    2. The `java.home` setting (from the Red Hat Java extension)
    3. The `JAVA_HOME` environment variable
    4. The `java` executable on `PATH`
-   [Maven](https://maven.apache.org/download.cgi) compatible with your chosen JDK
-   `galasactl` (optional but recommended) – required for the CLI integration commands described below. Install it from your preferred Galasa CLI distribution channel.

### Java 9+ note

For JDKs 9 and above, the extension automatically appends the necessary `--add-opens` flags so that the OSGi-based Galasa framework can run without `IllegalAccessException`. JDK 17 and 21 also receive `-Djava.security.manager=allow` and self-attach flags respectively.

## What is Galasa?

Galasa is an open source deep integration test framework for teams looking to give more power to their testers. What makes Galasa a deep integration test framework is its ability to support tests that cross system boundaries and reach into remote layers inaccessible to other testing tools.

Galasa has been architected to ensure that the routine tasks of writing and executing tests are straightforward. The more complex parts of tests (such as provisioning) are abstracted into other components that can be written by experts and easily distributed to the team.

## Overview of the Galasa extension features

### User configuration



1. Maven-local: If you have a local Maven repository to pull from you can specify this here to take priority over the remote Maven repository
2. Maven-remote: URI for remote Maven Repository
3. Overrides: A boolean that enables if you want to use your `overrides.propertis` in `.galasa`
4. Requestor: Defining the name of the Requestor when Requesting a Galasa Run
5. Version: The currently built Galasa version, you would like to use

### Launching a Galasa Test

There are multiple ways to launch a Galasa test in this extension, you are able to use the incode-button or are able to press the button in the upper-right side corner of your screen.

_Running a Galasa test requires you to have built the whole of Galasa for the version that you are currently writing a test for._

Click the `Debug Galasa Test` to start debugging your test. **Or** you can press the Galasa-icon in the upper-right corner to run the same opened test.

### Setting up custom Environment Properties


Environment properties are there for you to define specific properties that are to be used in `overrides.properties`-file in your `.galasa`-folder. These properties allow you to define specific meta-data for certain tests. You are able to switch between these environments and add properties with their associated values as you wish. If you have utilised an environment of properties fully you are able to even delete this environment.

1. Creating a new environment
2. Opening and activating this new environment and adding necessary environment variables for a Galasa test
3. These environment variables are the utmost layer of overriding your cps.properties

### Generating a testing-environment for running Simbank

**Simbank** simulates a mainframe application. It has been created to show off the hybrid and scalable capabilities of the Galasa Framework without having to deal with the complexities of connecting to an actual mainframe. It is a perfect start to learn and/or understand how the framework operates.

![Simbank initial screen](resources/readme/simplatform.png)

Simbank has been built inside the extension to showcase some of Galasa's capabilities and help you start writing your own Galasa tests.

You can connect with the Simbank-environment using a 3270-emulator and are able to interact it by running the provisioned Galasa tests.

##### This functionality is visible on the TEST RUNNER tab

_All Galasa-related files can be found in the .galasa folder under your user's root._

1. Click the _rocket-icon_ under local runs to launch an instance of Simbank running locally on your machine using the detected JDK (8-26).

2. Initialise your Galasa environment. (Setup Galasa Workspace icon under local runs) _This should have been done during the first launch of the Galasa extension, but can become malformed during runtime of the extension._

3. Initialise your workspace with the Simbank manager and the accompanied Galasa tests. (Create Simbank examples icon). You are able to give this package a desired name. _YOUR_PACKAGE_NAME_

4. First, perform a `mvn install` on _YOUR_PACKAGE_NAME_.manager, then `mvn install` on _YOUR_PACKAGE_NAME_.tests.

5. Set up your cps.properties with the correct properties to be able to run one of the provisioned tests. _The cps.properties is used for personalising specific elements for running Galasa Tests._ For running the IVT you will need to set up the following code. These cps.properties allow your tests to be performed on your locally running instance of Simbank that we had previously activated.


    ```cps.properties
    zos.dse.tag.SIMBANK.imageid=SIMBANK
    zos.dse.tag.SIMBANK.clusterid=SIMBANK

    simbank.dse.instance.name=SIMBANK
    simbank.instance.SIMBANK.zos.image=SIMBANK

    zos.image.SIMBANK.ipv4.hostname=127.0.0.1
    zos.image.SIMBANK.telnet.port=2023
    zos.image.SIMBANK.webnet.port=2080
    zos.image.SIMBANK.telnet.tls=false
    zos.image.SIMBANK.credentials=SIMBANK

    zosmf.server.SIMBANK.images=SIMBANK
    zosmf.server.SIMBANK.hostname=127.0.0.1
    zosmf.server.SIMBANK.port=2040
    zosmf.server.SIMBANK.https=false
    ```

    *You can also reach the Simbank instance using your 3270-emulator of choice.*


    Credentials must be coupled with these tests through the use of the `credentials.properties` file also in `.galasa`

    ```credentials.properties
    secure.credentials.SIMBANK.username=IBMUSER
    secure.credentials.SIMBANK.password=SYS1
    ```

6. Refresh the test runner tab and you should be able to see the provisioned Simbank Galasa Tests.
   Run these Simbank tests by pressing the run-icon next to any test and look at the process in the popped-up terminal.


## Galasa CLI integration

The extension surfaces every major area of `galasactl` as a VS Code command. Run them from the Command Palette (`Ctrl+Shift+P` / `Cmd+Shift+P`) and look for the **Galasa:** prefix. They can be wired up to keybindings or task definitions like any other VS Code command.

### Authentication

| Command | Description |
| --- | --- |
| `Galasa: Auth - Login` | Run `galasactl auth login` against the configured ecosystem. |
| `Galasa: Auth - Logout` | Run `galasactl auth logout`. |
| `Galasa: Auth - List Tokens` | Lists personal access tokens. |
| `Galasa: Auth - Revoke Token` | Revokes a specific token by id. |

### Test runs

| Command | Description |
| --- | --- |
| `Galasa: Runs - Prepare Portfolio` | Builds a portfolio file from one or more streams. |
| `Galasa: Runs - Submit Portfolio` | Submits a portfolio of tests to the ecosystem. |
| `Galasa: Runs - Submit Local` | Runs a test class locally via `galasactl runs submit local --class --obr`. |
| `Galasa: Runs - Get` | Retrieves details for a specific run. |
| `Galasa: Runs - Delete` | Deletes a run from the ecosystem. |
| `Galasa: Runs - Download Artifacts` | Downloads artifacts for a run. |
| `Galasa: Runs - Reset` | Re-queues a stuck or looping test. |
| `Galasa: Runs - Cancel` | Abandons a running test. |

### Local environment & projects

| Command | Description |
| --- | --- |
| `Galasa: Local - Init` | Runs `galasactl local init` to create `galasactl.properties` in `GALASA_HOME`. |
| `Galasa: Project - Create` | Scaffolds a new Galasa test project (Maven or Gradle, with optional features). |

### Configuration property store

| Command | Description |
| --- | --- |
| `Galasa: Properties - Get` | Retrieves properties by namespace (and optional prefix). |
| `Galasa: Properties - Set` | Creates or updates a property. |
| `Galasa: Properties - Delete` | Removes a property. |
| `Galasa: Properties - List Namespaces` | Lists available namespaces. |

### Resources, monitors, secrets, roles, users, streams

| Command | Description |
| --- | --- |
| `Galasa: Resources - Apply / Create / Update / Delete` | Manage ecosystem resources from a YAML file. |
| `Galasa: Monitors - Get / Set` | View or enable/disable service monitors. |
| `Galasa: Secrets - Get / Set / Delete` | Manage credentials in the secret store. |
| `Galasa: Roles - Get` | Lists roles defined in the service. |
| `Galasa: Users - Get / Set Role` | Manage user accounts and assigned roles. |
| `Galasa: Streams - Get / Delete` | Manage test streams in the service. |

All CLI commands honour the `galasa.cliPath`, `galasa.home`, and `galasa.bootstrap` settings as well as the standard `GALASA_HOME` and `GALASA_BOOTSTRAP` environment variables. Output is captured into the **Galasa** output channel; long-running commands are invoked in a dedicated terminal so you can interact with them.

## Settings reference

| Setting | Description |
| --- | --- |
| `galasa.javaHome` | Path to a JDK (Java 8-26). Overrides all other Java discovery sources. |
| `galasa.cliPath` | Path to the `galasactl` executable. If empty, the extension uses the one on `PATH`. |
| `galasa.home` | Overrides `GALASA_HOME`. |
| `galasa.bootstrap` | Overrides `GALASA_BOOTSTRAP` (file:// or HTTPS URL). |
| `galasa.maven-local` | Local Maven repository to take priority over the remote. |
| `galasa.maven-remote` | URL of the remote Maven repository. |
| `galasa.version` | Galasa version to use; `LATEST` resolves to the bundled symbolic version. |
| `galasa.requestor` | Identifier injected as the requestor on local runs. |
| `galasa.overrides` | Whether to use `~/.galasa/overrides.properties` for local runs. |

## Build, test, and release

This repository ships with a full GitHub Actions setup:

| Workflow | Trigger | What it does |
| --- | --- | --- |
| `.github/workflows/ci.yml` | Push / PR to `main`, `master`, `feature/**`, `bugfix/**`, `claude/**` | Lints (non-blocking), runs `tsc -p`, exercises the Java detection on a Java 8/11/17/21 matrix, packages a `.vsix` artifact. |
| `.github/workflows/codeql.yml` | Push / PR to `main`/`master`, weekly cron | CodeQL `security-and-quality` analysis for JavaScript/TypeScript. |
| `.github/workflows/release.yml` | Tag push `v*.*.*` or `workflow_dispatch` | Resolves the version, syncs `package.json`, packages a `.vsix`, creates a GitHub Release with the asset, and (optionally, if `VSCE_PAT` / `OVSX_PAT` secrets are configured) publishes to the VS Code Marketplace and Open VSX. |

### Cutting a release

1. Bump `package.json` version (or rely on the version already there).
2. Update `CHANGELOG.md`.
3. Tag and push:
   ```bash
   git tag v0.15.0
   git push origin v0.15.0
   ```
4. The release workflow will build the `.vsix`, attach it to a new GitHub Release, and (when secrets are configured) publish to the marketplaces.

### Required secrets for marketplace publishing

| Secret | Purpose |
| --- | --- |
| `VSCE_PAT` | Personal access token from https://dev.azure.com (`Marketplace > Publish` scope) for the VS Code Marketplace. |
| `OVSX_PAT` | Personal access token from https://open-vsx.org for Open VSX. |

If a secret is absent, the workflow simply skips the corresponding publish step.

### Local packaging

```bash
npm install
npx tsc -p ./
npx --yes @vscode/vsce package
```

This produces a `galasa-plugin-<version>.vsix` you can install with `code --install-extension galasa-plugin-<version>.vsix`.
